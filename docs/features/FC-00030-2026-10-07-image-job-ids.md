# FC-00030 — Join review rows to images by job id, not filename

**Date:** 2026-10-07 · **Slice:** S · **Risk:** Low · **Status:** done · **Affected entities:** All

## What
Every uploaded image gets a unique job id; every OCR row records the id of the image it came from. Thumbnails, per-image re-run and retry cleanup use that id instead of the filename.

## Why
Two different images can share a filename (pasted `image.png`, re-sent WhatsApp photos, a later batch with the same name). The filename join showed the wrong thumbnail, and re-running OCR on one image deleted the other image's rows.

## Fix
- `_newJobId()`; jobs created in `runOcrForEntity` carry `id`.
- OCR rows get `imageJobId` (main run and retry paths); `processReviewRow` keeps it.
- `_rowFromJob(r, job)` — id match when both have one, else filename (legacy rows).
- `_findJobForRow(entIdx, rowOrName)` — row (by `imageJobId`), job id, or a filename only when exactly one job has it.
- Retry / re-run cleanup filters by `_rowFromJob`. File-list retry buttons and review-table re-run buttons pass the job id.
- `renderOcrFileList` accumulates jobs across batches (FC-00011 append used to replace the list, losing earlier thumbnails and re-run targets).

## Where in UI
Actuals Intake: OCR file list, review-table thumbnails and re-run buttons.

## Touches
ocr, display

## Risk
Low — join key change only; no calculation touched.

## Reversibility
Fully reversible via one revert commit.

## Definition of Done
1. Two images with the same name show their own thumbnails.
2. Re-running one never deletes the other's rows.
3. Jobs from every batch stay listed and re-runnable.
4. Rows without a job id (re-imported intake) still find a uniquely named image.
5. Existing tests pass; new tests pass.

## Out of scope
De-duplicating identical re-uploads. Exporting the job id.
